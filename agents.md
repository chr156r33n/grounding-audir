# AGENT\.md — Grounding Source Observatory

## Mission

Build a **Streamlit web application** that lets a user test one or more grounding/search phrases across multiple AI web\-grounding services and inspect whether a target domain is surfaced or cited\.

The core research question is:

> For this query, does each grounding/search ecosystem expose or cite the target domain, and what evidence does that provider make observable about the search/retrieval process?

This is **not a rank tracker**\. Do not pretend retrieval order, citation order, or grounding\-source order is equivalent to conventional organic search rank\.

The application should prioritise:

1. methodological correctness;
2. transparent observability;
3. provider\-by\-provider evidence;
4. useful comparison;
5. resilience when providers fail or expose different telemetry\.

The first implementation must be a **local\-first Streamlit app**\. Do not introduce a separate frontend, database, Redis, Celery, Kubernetes, user authentication, scheduling, or other infrastructure unless explicitly requested later\.

---

# 1\. Product requirements

The Streamlit app must allow the user to:

1. Enter a grounding/search phrase\.
2. Enter a target domain, hostname, or URL prefix\.
3. Select which grounding/search providers to run\.
4. Enter API credentials/configuration for each selected provider in the UI\.
5. Run all selected providers concurrently\.
6. See progress and completion status per provider\.
7. See a comparison matrix showing whether the target domain was:
  - observed in retrieval/search results, where this is actually observable;
  - cited in the model response, where citations are exposed\.
8. Expand each provider to inspect all available detail:
  - generated/fan\-out search queries;
  - returned/retrieved sources;
  - citations;
  - snippets/chunks/content where available;
  - final model response where relevant;
  - provider metadata;
  - explicit notes for stages the provider does not expose\.
9. Export normalised run data as JSON and CSV\.
10. Complete a run even if one or more providers fail\.

The primary UX should answer the simple question quickly:

> **Was the target domain cited? Yes / No / Unknown / Not Applicable**

Then allow the user to inspect the evidence underneath\.

---

# 2\. Core methodological rule

Different providers expose different windows into their grounding pipelines\.

Never infer an unobservable stage\.

For every field such as `retrieved`, `cited`, or `search_performed`, distinguish between:

- `YES`
- `NO`
- `UNKNOWN`
- `NOT_APPLICABLE`

Do **not** use plain booleans internally for these states\.

Example:

```text
Target retrieved: UNKNOWN
Target cited: NO
```

means:

> The API did not expose enough retrieval data to determine whether the target was retrieved, but the target was not present in the exposed citations.

This is very different from:

```text
Target retrieved: NO
Target cited: NO
```

Never collapse `UNKNOWN` into `NO`\.

---

# 3\. Terminology

Use these terms consistently throughout code, UI, exports, tests, and documentation\.

## Input phrase

The phrase entered by the user\.

## Generated query

A search query or fan\-out query generated by a model/tool before web retrieval\.

## Search result / retrieved source

A URL/domain exposed by the provider as part of web search or retrieval\.

## Grounding content / chunk

A piece of returned page content or extracted text exposed by the provider for grounding\.

## Citation

A source URL explicitly attributed by the provider to part of the generated answer\.

## Target match

A source/citation matching the user\-configured domain, hostname, or URL prefix\.

## Search rank

Only use this term for a conventional search API that explicitly returns ranked SERP results\.

## Retrieval position

Order in which a retrieval/search API returns sources\. Do not label this as rank unless the provider explicitly defines it as ranking\.

## Citation position

Order in which citations occur in a response\. This is not search rank\.

## Not observable

The provider/API does not expose that stage\.

# 5\. Important current provider caveats

Provider APIs change\. Before implementing an adapter, check the provider’s current official documentation and record the API surface/model used\.

Do not rely blindly on old examples or assumptions in this file\.

## Gemini / Google Search

As of the current Gemini API documentation, the Google Search tool can expose:

- generated search queries via a Google search call;
- a search result step;
- inline URL citation annotations on model output;
- citation offsets/segments;
- search suggestions markup\.

The current documented Interactions API page does **not** document the older `groundingChunks` / `groundingSupports` structures on that surface\.

Therefore:

- implement what the current SDK/API actually exposes;
- treat detailed retrieval chunks as `UNKNOWN` / unsupported if they are not present;
- do not fabricate chunks by fetching cited URLs yourself;
- preserve raw responses so richer fields can be parsed later if Google changes the schema\.

Official reference:
https://ai\.google\.dev/gemini\-api/docs/google\-search

## Microsoft Foundry Web Search

Treat **Microsoft Web Search** as a separate provider from explicit Bing Grounding\.

The current Foundry Web Search tool:

- provides public\-web grounding;
- can return inline URL citations;
- does not require a separate Bing grounding resource/project connection for the general web\-search scenario;
- may not expose a raw ranked search\-result set equivalent to a conventional Bing SERP\.

Do not assume raw retrieval is visible unless the response actually exposes it\.

Official reference:
https://learn\.microsoft\.com/en\-us/azure/foundry/agents/how\-to/tools/web\-search

## Microsoft Grounding with Bing Search

Treat this as a distinct provider\.

Important:

- it requires Foundry/Azure configuration beyond a simple API key;
- it can expose generated Bing search\-query information and citations;
- Microsoft explicitly states that Grounding with Bing Search does **not** return the grounding tool output to developers/end users;
- therefore raw retrieved content/results should usually be `UNKNOWN`, not `NO`;
- display requirements may require both website URLs and Bing search\-query URLs\.

Official reference:
https://learn\.microsoft\.com/en\-us/azure/foundry/agents/how\-to/tools/bing\-tools

## OpenAI Web Search

The current Responses API web\-search tool can expose:

- web\-search actions;
- URL citations;
- a `sources` field containing URLs consulted during search when explicitly requested through the include mechanism;
- potentially more sources than appear as final inline citations\.

Therefore OpenAI can often distinguish:

- observed/consulted source;
- cited source\.

Official reference:
https://developers\.openai\.com/api/docs/guides/tools\-web\-search

## Brave LLM Context

When implemented, Brave LLM Context is valuable because it is explicitly designed to return pre\-extracted context/chunks for LLM grounding\.

It can expose:

- relevant URLs;
- extracted content;
- AI\-oriented context rather than merely human\-facing SERP listings\.

Official reference:
https://api\-dashboard\.search\.brave\.com/documentation/services/llm\-context

## Tavily

When implemented, use the current official Search API and capture returned result metadata/content without pretending it is a final\-model citation unless a separate generation layer explicitly cites it\.

Official reference:
https://docs\.tavily\.com/documentation/api\-reference/endpoint/search

# 7\. Credential handling

For the initial local Streamlit version, credentials should be entered in the UI\.

Requirements:

- use password\-type inputs for secrets;
- keep secrets only in Streamlit session state / process memory;
- never write API keys/tokens to disk;
- never include secrets in exports;
- never include secrets in logs;
- never include secrets in exception messages rendered to the UI;
- never put credentials into prompts;
- never commit secrets to Git;
- do not require `.env` for the MVP, although optional environment\-variable fallback is acceptable later\.

Provider configuration is not always just one API key\.

The provider architecture must allow each provider to declare its own fields\.

Example conceptual schema:

```python
ProviderField(
    key="api_key",
    label="API key",
    secret=True,
    required=True,
)
```

For Microsoft providers, support the current required Foundry/Azure configuration rather than pretending a single key is enough\.

Potential fields can include:

- project endpoint;
- model deployment name;
- connection name or connection ID;
- authentication method/token;
- market/language settings\.

Do not hardcode provider credential inputs into one giant `app.py` conditional if a registry\-driven approach is reasonably simple\.

# 13\. Domain and URL matching

This is research\-critical\.

Do not use string containment such as:

```python
if target in url:
```

Use URL parsing plus Public Suffix List\-aware domain extraction\.

Recommended dependency:

```text
tldextract
```

Support three match modes\.

## Root domain

Target:

```text
fourseasons.com
```

Matches:

```text
https://www.fourseasons.com/
https://press.fourseasons.com/
https://fourseasons.com/hongkong/
```

## Exact hostname

Target:

```text
www.fourseasons.com
```

Does not match:

```text
press.fourseasons.com
```

## URL prefix

Target:

```text
https://www.fourseasons.com/hongkong/
```

Matches only URLs under the configured prefix after conservative normalisation\.

# 14\. URL normalisation

Retain the provider’s original URL\.

Store both:

```text
raw_url
normalized_url
```

Suggested conservative normalisation:

- lowercase hostname;
- remove URL fragment;
- normalize obvious trailing\-slash equivalence;
- optionally remove known tracking parameters such as UTM parameters for analytical deduplication;
- do not rewrite meaningful query parameters;
- do not automatically resolve redirects\.

Do not destroy raw evidence\.

The same page may appear as:

```text
https://example.com/foo
https://example.com/foo/
https://example.com/foo?utm_source=x
```

The analytical layer may deduplicate these, but exports should preserve the observed URL too\.

---

# 15\. Redirect handling

Do not automatically crawl/follow every returned citation URL in MVP\.

Why:

- adds latency;
- adds extra network requests;
- changes the experimental boundary;
- may hit blocked/unsafe pages;
- may contaminate evidence by introducing information the grounding provider never exposed\.

If redirect resolution is added later, make it an explicit optional post\-processing step and preserve:

```text
observed_url
resolved_url
```

Never replace the observed provider evidence\.

---

# 16\. Citation matching rule

A target is `cited = YES` only if the provider explicitly exposes a citation/attribution URL that matches the target\.

Do not infer a citation because:

- the target domain string appears in answer text;
- the brand is mentioned;
- a source was retrieved;
- the model names a page without a citation annotation\.

Keep separate dimensions:

```text
mentioned
retrieved
cited
```

`mentioned` can be added later if useful, but do not conflate it with citation\.

---

# 17\. Retrieval matching rule

A target is `retrieved = YES` only when:

- the provider explicitly exposes a retrieved/consulted source list;
- at least one observed retrieved source matches the target\.

A target is `retrieved = NO` only when:

- the provider exposes a sufficiently complete retrieval/source list for that request;
- the target is not present\.

Use `retrieved = UNKNOWN` when:

- the provider does not expose retrieval;
- the response only exposes citations;
- the adapter cannot safely determine completeness\.

This rule is mandatory\.

# 18\. Search\-performed rule

Where possible, expose:

```text
search_performed
```

Possible values:

- YES
- NO
- UNKNOWN
- N/A

Some model/tool combinations decide whether to search\.

For a grounding research tool, force web\-search usage when the provider supports a documented `required`/forced tool option\.

Do not invent undocumented provider parameters\.

If forcing search is impossible:

- use explicit prompt wording requiring fresh web search;
- inspect returned tool events;
- report whether search appears to have occurred\.

A run with no search must not be silently reported as “target not retrieved”\.

# 22\. Concurrent execution

Provider calls must run concurrently\.

For Streamlit, a pragmatic first implementation is a `ThreadPoolExecutor` because many provider SDKs are synchronous and the work is network\-bound\.

Suggested approach:

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=len(selected_providers)) as executor:
    future_map = {
        executor.submit(run_provider, provider, request, config): provider
        for provider in selected_providers
    }

    for future in as_completed(future_map):
        provider = future_map[future]
        result = future.result()
        # Update Streamlit UI from the main thread only.
```

Alternatively, use `asyncio` if all adapters are genuinely async\.

Important:

- do not update Streamlit UI from worker threads;
- provider workers return data;
- the main Streamlit thread consumes completed futures and updates status placeholders\.

Do not call providers sequentially\.

# 23\. Provider timeouts

Each provider must have an independent timeout\.

Suggested default:

- 45 seconds per provider\.

This can later become configurable\.

A timeout must create a failed/timed\-out provider result, not crash the overall experiment\.

Example:

```text
Gemini                Complete       4.8s
OpenAI                Complete       6.1s
Microsoft Web         Complete       9.7s
Bing Grounding        Timed out      45.0s
```

The matrix should still render successful providers\.

# 24\. Retry behaviour

Implement conservative retries only for clearly retryable failures\.

Examples:

- HTTP 429;
- transient 5xx;
- network reset\.

Use exponential backoff with jitter\.

Suggested:

- max 2 retries;
- do not retry authentication errors;
- do not retry invalid configuration;
- respect provider Retry\-After headers\.

Record retry count in metadata\.

Do not let retries make the app appear frozen\. Status text can show “retrying”\.

# 30\. Detailed\-result policy

The user explicitly wants to expand/review “chunks or detailed results”\.

Interpret this as:

> Show the most detailed evidence each provider actually exposes.

Do not promise identical “chunks” across all providers\.

Examples:

- OpenAI may expose consulted source URLs and citations;
- Brave LLM Context may expose extracted context;
- Gemini may expose generated queries and citations on the current documented API surface;
- Microsoft Bing Grounding may expose citations/query URLs but withhold raw tool output\.

The UI should make these differences obvious\.

---

# 31\. Raw\-response preservation

Preserve each provider’s raw API response in memory where possible\.

Pipeline:

```text
RAW PROVIDER RESPONSE
        ↓
PROVIDER PARSER
        ↓
NORMALISED GROUNDING RUN
```

Reasons:

- provider APIs change;
- parsers may later be improved;
- research needs reproducibility;
- useful telemetry may exist before the application understands it\.

For MVP:

- keep raw responses in session memory;
- optionally allow JSON export;
- do not create a persistent database\.

Sanitise credentials before raw\-response storage/export if there is any possibility they appear\.

# 32\. Provider adapter interface

Every provider must implement a common interface\.

Suggested:

```python
class GroundingProvider(ABC):
    id: str
    name: str
    capabilities: ProviderCapabilities

    @abstractmethod
    def validate_config(self, config: dict) -> list[str]:
        ...

    @abstractmethod
    def run(
        self,
        request: GroundingRequest,
        config: dict,
    ) -> GroundingRun:
        ...

    @abstractmethod
    def parse_response(
        self,
        raw_response,
        request: GroundingRequest,
    ) -> GroundingRun:
        ...
```

If using async:

```python
async def run(...)
```

is acceptable\.

Keep provider SDK/API code out of Streamlit UI modules\.

- multiple generated queries;
- one target citation;
- no target citation;
- no search;
- malformed/changed optional metadata\.

# 40\. Search\-provider vs grounding\-provider type

class ProviderType(str, Enum):

A provider may issue the same generated query multiple times\.

Preserve raw events, but expose:

Never silently discard repeated calls from raw evidence\.

# 43\. Duplicate URL handling

The same URL may occur:

- multiple times in source lists;
- across generated queries;
- as both retrieved source and citation\.

Track:

- observed count;
- associated generated queries where possible;
- retrieved state;
- cited state\.

# 44\. Error handling

One provider failure must never fail the entire run\.

Return a structured `GroundingRun` with error metadata\.

Handle:

- invalid credentials;
- expired tokens;
- rate limits;
- provider 4xx/5xx;
- timeout;
- unsupported model;
- missing Azure connection;
- parser failures;
- missing optional fields;
- provider changes;
- search not triggered\.

Render human\-readable messages\.

Do not expose full stack traces by default in the user UI\.

Allow a developer/debug expander if useful\.

---

# 45\. Parser robustness

Provider parsers must be defensive\.

Use `.get`, `getattr(..., None)`, schema validation, or equivalent patterns\.

A missing optional field should not crash a run\.

Distinguish:

- unsupported field;
- supported but empty;
- parser failure\.

Preserve unexpected raw fields\.

Do not assume:

- every output item has annotations;
- every citation has title;
- every URL is valid;
- every search call has queries;
- every provider searches exactly once\.

---

# 46\. Security and prompt\-injection handling

Treat all retrieved web/search content as untrusted\.

Rules:

- never execute HTML/JavaScript returned by a provider;
- render provider HTML as escaped text unless a provider explicitly requires a safe sanctioned widget and implementation has been reviewed;
- do not feed retrieved content into local functions that can access credentials;
- never allow retrieved instructions to modify application configuration;
- never expose secrets to models;
- never interpolate secrets into page output;
- sanitise any raw markup\.

Do not blindly render provider\-provided HTML with unsafe HTML enabled\.

For Streamlit, avoid `unsafe_allow_html=True` for untrusted provider content\.

# 68\. Final implementation principle

The application should answer two different questions separately:

> **Did this provider cite my target?**

and:

> **What can this provider actually show me about how it searched/retrieved information?**

The first should be easy to scan\.

The second should be deeply inspectable\.

The tool must never sacrifice the second question’s accuracy merely to produce a neat Yes/No dashboard\.

A provider saying:

```text
Retrieved: UNKNOWN
Cited: NO
```

is a valid and useful result\.

It means the observability gap belongs to the provider/API, not to the target domain\.

That distinction is central to the whole application\.
